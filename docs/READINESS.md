## Recorded local verification

The following checks used isolated test fixtures during this handover; they did not create deployed user accounts:

- `services/core/manage.py test api --noinput`: **91 Django tests** passed (2 skipped), including authorization, idempotency, provider suspension, privacy/adulthood transition, operations, financial invariants, scheduler leases and revoked clinician access.
- `services/assistant` and `services/diagnostic` test suites: **21 tests** passed.
- `node scripts/smoke-api.mjs`: **54 API checks** passed after the final core rebuild, covering isolation, clinician-record authority, idempotency, revocation, booking, duplicate capture and cancellation.
- `npm run test:video`: two browser participants exchanged decoded audio/video, reconnected after a forced signaling interruption, completed booking → test-only payment event → signed note → follow-up, and denied a fresh join after consent revocation.
- `npm run test:restore`: restored a disposable database and verified signed-note immutability, ledger state, revocation, family isolation and booking constraints.
- `npm run test:load`: 80 authorized child-record reads with 8 concurrent local clients completed without leakage or hard errors. This is a bounded local smoke check, not a capacity claim.
- `apps/web`: typecheck, tests and production build passed. Contrast ratios recorded by the check are at least 5.14:1 for tested text pairs.
- `apps/mobile`: typecheck and 20 unit/transport tests passed; Expo bundles were exported for Android, iOS and web. No physical device test is claimed.
- `dev-service-check.py`, `dev-check.py`, and OpenAPI contract checks passed locally. Firebase verification, recovery, and MFA require a configured project acceptance run.

Latest security remediation: a clinician whose child-record grant is revoked now loses appointment and payment metadata as well as records; only active doctors and therapists can create clinical records, and only their author can edit an unsigned draft. The clients reject unsafe service URLs and avoid ambient cookies/referrers/caches. Firebase profile/custom claims are not used for authorization; the core maps only verified identities to server-owned accounts.

## Known limits that intentionally fail closed

- No licensed autism questionnaire content is bundled. The licensed catalogue entry stays disabled until rights and validated implementation are supplied.
- No diagnostic model is promoted. The normal prediction response is an explicit abstention, never a diagnosis.
- Patient-record AI remains disabled until the required provider controls and review are active. Conversations are not training data automatically.
- Local self-hosted LiveKit can remove an active participant and deny a fresh token, but cannot invalidate a previously cached JWT. Production configuration only accepts a LiveKit Cloud endpoint until an equivalent revocation mechanism is independently verified.
- Production bookings and policy-dependent finance operations return unavailable if `BUSINESS_POLICY_PATH` does not point to a valid approved production policy.
- No real payment, KYC, provider transfer, provider credential, patient enrollment, SMS/email delivery, or push delivery is enabled.
- The current web client keeps a Firebase bearer token in `sessionStorage`. A public deployment requires a backend-for-frontend session using secure HttpOnly cookies, CSRF protection and a tested content-security policy.
- The Supabase/Vercel scheduler dispatches the durable outbox and bounded reminder/rate-limit maintenance, but it does not provide private storage scanning, provider egress controls, image/SBOM vulnerability gates, or operational log-redaction verification. These require separately approved managed services and release evidence.
- Supabase Data API is disabled, so browser clients cannot query database schemas. `pg_net` remains an extension-owned, non-relocatable schema and can retain the provider's `extension_in_public` advisory; the private scheduler wrapper is not API-exposed.
- Firebase password policy, email-enumeration protection, authorized domains and multi-factor enrollment must be configured and acceptance-tested before public enrollment. The clients require a 12-character password.
- The production username/password bridge is unavailable and returns a generic credential `403` until `TRUST_PROXY_HEADERS=true` is set behind an independently verified trusted proxy that supplies a non-user-controlled client address (`X-Vercel-Forwarded-For` on Vercel, or verified `X-Forwarded-For` elsewhere), and the existing `reminders` scheduler heartbeat is fresh. Its rate-limit keys are HMACed with the separately rotatable `USERNAME_RATE_LIMIT_HMAC_KEY`, or the server-only Django secret when omitted.
- Supabase password hashes cannot move to Firebase. A fresh verified Firebase identity matching a legacy local email receives `firebase_identity_link_review_required`; `POST /v1/auth/identity/link/` cannot complete the attachment. Support must collect independent identity proof before an authorized operator writes an audited mapping, so an email-only Firebase identity never opens legacy care records.
- Records are retained after an account-closure request under explicit legal/financial/clinical holds. The workflow does not falsely report medical-record erasure.

## Release decision inputs

Before enabling any production capability, record the accountable person, evidence reference, review date and rollback owner for the applicable release gate. The minimum release package includes approved clinical intended use and claims, privacy/retention policy, contracts with each processor, financial and provider operations ownership, accessible English/Malayalam content, security review, signed mobile release artifacts, live vendor tests, monitored incident coverage, and an isolated restore/reconciliation drill.

For the diagnostic feature, these product gates are insufficient: a separate evidence, clinical, regulatory and model-promotion decision is mandatory. Until then, NeuroNest can provide records, care coordination, education and support without representing a questionnaire or model as a diagnosis.

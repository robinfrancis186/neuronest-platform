# Age-based developmental check-ins

The Milestones web page uses the core API's versioned, selected CDC-based prompts. The core computes completed calendar months from the child's recorded birth date in Asia/Kolkata. It uses the last reached age band, never the next one: a five-month-old receives the four-month prompts. Month-end birthdays use the final day of a shorter month. Bands are 2, 4, 6, 9, 12, 15, 18, 24, 30, 36, 48 and 60 months, supported through 71 completed months. Outside that range, no checklist is presented; concerns can be discussed with a clinician at any age. Prematurity is not automatically adjusted because gestational age is not recorded; the page directs families to ask their clinician.

`services/core/api/milestone_catalog.json` contains six selected prompts per band, adapted from the individually linked CDC pages checked on 25 October 2026. These are a subset, not the complete CDC checklist. The sensory and daily-living domain groupings and Malayalam translations are NeuroNest adaptations. They require clinical/editorial review; they are not an official CDC translation or evidence of a validated screening instrument. Earlier checkbox observations remain in observation history and reports. They are not silently converted into complete new check-ins because an unchecked box cannot establish a No response.

## Save and review

- `GET /v1/milestone-checkins/catalog/?child=<id>` returns the current band, catalogue version, age and AI configuration flag.
- `POST /v1/milestone-checkins/` accepts the child, catalogue version, band, one explicit answer per prompt (`yes`, `in_progress`, `not_yet`, `unsure`), and explicit boolean `parent_concern` and `skill_loss` answers.
- Incomplete, additional, unsupported, stale-band or stale-version answers are rejected. The server derives age and summary; clients cannot supply an interpretation or AI result.
- `GET /v1/milestone-checkins/?child=<id>` and the detail endpoint retrieve immutable dated snapshots with their original question labels and source. They use the `observations` permission, including scoped caregivers and separately authorized clinicians. Only a parent with active observations authority can submit. PATCH and DELETE are unavailable.
- Authorized child exports include check-ins only when observations access is also present. Existing reviewed retention/deletion policy applies to this child-related data.

The summary reports raw answer counts and the actual answers, not a clinical score. In-progress, Not yet and Not sure remain distinct from Yes. Any non-Yes answer or parent concern recommends clinician discussion; reported skill loss prompts timely professional contact without waiting for submission or AI. All-Yes wording reports only the selected skills and explicitly cannot confirm typical development or rule out concerns. These recommendations are transparent monitoring prompts, not a validated triage algorithm.

## Optional AI explanation

`POST /v1/milestone-checkins/<id>/explain/` requires fresh explicit consent, parent observations access and the dedicated `MILESTONE_AI_ENABLED=true` setting on the core and assistant. This project-demo feature uses OpenAI Decisions (`gpt-6-luna`) to classify the reported answer pattern; it does not use the clinical prediction service or open general clinical-record AI. `PATIENT_AI_ENABLED` and `ALLOW_PATIENT_AI` remain disabled.

The authenticated core calls the assistant's strict `/milestone-explanation` endpoint with only six public question labels, categorical answers, checklist band, language and follow-up flags. No names, birth dates, subject/check-in identifiers, request identifiers, clinical records or free-text notes are sent. The OpenAI Decisions call receives only public question labels, categorical answers and the checklist band. Labels use the requested language; no child identifier, name, birth date, concern flag, lost-skill flag or private note is sent to OpenAI. The assistant applies follow-up flags locally, preserving lost-skill escalation even if generated text omits it.

The assistant reuses the server-only `OPENAI_API_KEY` and the existing authenticated route; no new SDK dependency is needed. It calls `POST https://api.openai.com/v1/decisions` with the exact model `gpt-6-luna` and one named `choice` question (`response_pattern`). The allowed categories describe only recorded answers: `all_observed`, `some_not_yet`, or `emerging_or_uncertain`. These categories do not estimate development or clinical risk. Decisions is a typed classification endpoint, not a clinically validated prediction model. See [official API documentation](https://developers.openai.com/api/reference/resources/decisions/methods/create).

Both assistant and core compare the returned category with the saved answer pattern. A refusal, wrong category/model, malformed result or provider failure is unavailable rather than a guessed success. Returned confidence and probability fields are discarded: they are not sent to the browser, stored with the result, or shown as health probabilities. The displayed explanation uses the saved question labels in four distinct answer groups and fixed follow-up text, not unconstrained model prose. The existing educational source-review rules and general clinical-record AI gates remain unchanged.

Only successful reviews are stored. A repeat request for the same check-in/language/method/model reuses that review; previous Responses explanations remain visible in saved history but do not masquerade as Decisions results and are refreshed only on explicit request. Access and consent are checked before reuse, and authority is rechecked after a provider call. The existing JSON field stores the method, model and answer category; no migration is needed. A failed review leaves the factual summary intact. Only authorized parents can request a review; clinicians remain read-only.

This is developmental monitoring. A validated screening instrument and suitable clinical evaluation are separate capabilities; no diagnostic model is promoted by this feature.

## Verification and deployment

Core: `python manage.py test api.test_milestones --noinput` (from `services/core`). Assistant: `python -m unittest discover -s tests` (from `services/assistant`). Web: `node scripts/check-milestones.mjs` (from `apps/web`); this uses synthetic API fixtures and a local browser, not live patient records or an actual provider response. Backend tests separately cover persistence, immutable snapshots, scopes, exports, stale age bands and disabled AI. Assistant tests use mocked provider outputs to verify refusal and generation paths. These tests do not establish clinical validity.

Deploy the new core migration `0012_milestonecheckin` before publishing the updated web client. Deploy the assistant update and configure its OpenAI key before enabling the dedicated milestone flag on both services. The catalogue file must accompany the core Python package; it is inside `api/` for the existing Docker/Vercel packaging. Production migration 0012 was applied in the earlier release. On 26 October 2026, the dedicated OpenAI explanation route, core flag and web interface were deployed. A clearly synthetic profile in the test account completed the live browser → core → assistant → OpenAI → persisted result flow; the explanation remained available after refresh. This verifies demo integration, not clinical validity or every provider failure mode. Native mobile UI remains unchanged; its shared API types are regenerated.
